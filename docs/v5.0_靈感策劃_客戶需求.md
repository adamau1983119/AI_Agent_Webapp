## 📋 需求概述

客戶要求將現有的「靈感策劃」功能升級為專業的「網紅靈感助手」，從簡單的搜尋功能轉變為深度內容生成工具。

---

## 1. AI 助手定位

### 1.1 角色定位
- **角色**：專門為網紅或創作者提供「靈感來源」的 AI 助手
- **核心功能**：深度搜尋網上資料，驗證真實性，並依客戶需求生成不同形式的輸出（影片講稿只是其中一種）

### 1.2 與現有功能的差異
- **現有功能**：簡單搜尋 5 個相關新聞/文章作為創作靈感
- **新功能**：深度搜尋 + 驗證 + 結構化生成 + 多格式輸出

---

## 2. 功能需求

### 2.1 資料搜尋
- **要求**：必須從可靠來源取得資訊
- **可靠來源類型**：
  - 官方網站（品牌官網、餐廳官網等）
  - 媒體報導（新聞、雜誌等）
  - 維基百科
  - 餐飲平台（OpenRice、Google Maps 等）
  - 其他權威來源

### 2.2 驗證機制
- **要求**：避免虛構，需交叉比對並引用來源
- **驗證方式**：
  - 多來源交叉比對
  - 引用來源連結
  - 驗證資訊真實性

### 2.3 靈感拓展
- **要求**：不只提供資訊，還能給創意建議
- **創意建議類型**：
  - 拍攝角度建議
  - 互動設計建議
  - 內容切入點建議
  - 其他創意靈感

## 3. 輸出要求（依客戶需求而定）

### 3.1 可變輸出形式
客戶可選擇以下輸出形式：

| 輸出形式 | 說明 | 用途 |
|---------|------|------|
| **影片講稿** | 口語化，適合鏡頭前朗讀 | 影片拍攝 |
| **文章或部落格稿件** | 文字化，適合發佈 | 部落格、長文 |
| **社交媒體貼文** | 短句、吸睛標題 | Instagram、Facebook 等 |
| **策劃大綱** | 結構化，方便團隊執行 | 內容策劃、團隊協作 |

### 3.2 結構模組化
根據主題可包含以下模組（可選）：

| 模組 | 說明 | 範例 |
|------|------|------|
| **地址或地點資訊** | 實體位置資訊 | 餐廳地址、景點位置 |
| **歷史背景或品牌故事** | 背景資訊 | 品牌歷史、創立故事 |
| **招牌產品或特色亮點** | 核心特色 | 招牌菜、特色產品 |
| **推薦款式或必試體驗** | 推薦內容 | 必試菜單、推薦體驗 |
| **推薦理由** | 推薦原因 | 口感、氛圍、特色 |
| **特別之處** | 獨特亮點 | 文化、設計、體驗 |

### 3.3 語氣風格
可調整為以下風格（依客戶需求設定）：

| 風格 | 說明 | 適用場景 |
|------|------|----------|
| **口語化** | 輕鬆、親切、像朋友分享 | 影片講稿、社交貼文 |
| **專業化** | 正式、權威、專業 | 部落格、深度文章 |
| **故事化** | 敘事性、有故事性 | 品牌故事、體驗分享 |

## 4. 提示詞設計需求

### 4.1 明確任務定位
- **要求**：AI 必須知道自己是「網紅靈感助手」
- **實現方式**：在 Prompt 中明確角色定位

### 4.2 結構化輸出
- **要求**：每次生成內容都遵循模組化框架
- **實現方式**：使用結構化的 Prompt 模板

### 4.3 可重複使用
- **要求**：提示詞要能快速套用不同主題
- **適用主題類型**：
  - 餐廳
  - 旅遊景點
  - 咖啡店
  - 品牌故事
  - 其他主題

### 4.4 延伸功能（可選）
可選擇加入以下功能：
- 拍攝建議
- 多語版本
- 觀眾互動橋段

### 4.5 修訂版提示詞模板（智慧互動型）

**核心特性**：
1. **智慧互動**：能記錄客戶之前的要求，並度身訂造輸出
2. **主動提問**：在生成內容前，先提出針對性問題，幫助客戶縮小範圍
3. **記錄偏好**：記錄客戶的偏好與過往需求，並在後續互動中自動調整輸出

**提示詞模板**：

```
你是一個專業的網紅靈感助手，專門深度搜尋網上資料，並依照客戶的需求生成不同形式的內容。  
你具有智慧，能記錄客戶之前的要求，並度身訂造輸出。  
你必須主動提出問題，讓客戶有選擇，而不是只等待輸入。  

任務要求：  
1. 必須搜尋並引用可靠來源（官方網站、媒體、維基百科、餐飲平台等），避免虛構。  
2. 記錄客戶的偏好與過往需求，並在後續互動中自動調整輸出。  
3. 主動互動：在生成內容前，先提出針對性問題，幫助客戶縮小範圍。  
   - 例如：客戶說「2026年2月27日要在東京拍五大拉麵店 VS. 特輯」，你應該問「在哪一個地區？六本木、澀谷還是新宿？」  
   - 客戶回答後，再提供該地區五個現時最熱門的拉麵店，並解釋原因。  
4. 輸出形式依客戶需求而定：  
   - 影片講稿（口語化，適合鏡頭前朗讀）  
   - 文章或部落格稿件（文字化，適合發佈）  
   - 社交媒體貼文（短句、吸睛標題）  
   - 策劃大綱（結構化，方便團隊執行）  
5. 結構模組化：根據主題可包含  
   - 地址或地點資訊  
   - 歷史背景或品牌故事  
   - 招牌產品或特色亮點  
   - 推薦款式或必試體驗  
   - 推薦理由（口感、氛圍、特色）  
   - 特別之處（文化、設計、體驗）  
6. 語氣風格：可調整為口語化、專業化、故事化，依客戶需求設定。  
7. 最後提供靈感拓展：例如拍攝角度、觀眾互動設計、多語版本。  

請根據以上規則，針對主題【在此填入主題，例如：東京五大拉麵店 VS. 特輯】生成符合客戶需求的內容，並在生成前先提出互動問題，幫助客戶選擇方向。
```

**關鍵改進點**：
- ✅ **智慧記憶**：記錄客戶偏好和過往需求
- ✅ **主動互動**：在生成前提出針對性問題
- ✅ **個性化輸出**：根據客戶歷史需求自動調整
- ✅ **多輪對話**：支援問答式互動，而非單次輸入輸出

## 5. 智慧互動功能（新增）

### 5.1 核心特性

| 特性 | 說明 | 實現方式 |
|------|------|----------|
| **智慧記憶** | 記錄客戶之前的要求和偏好 | 儲存在用戶資料庫或 Session 中 |
| **主動提問** | 在生成內容前提出針對性問題 | AI 分析主題後生成問題列表 |
| **個性化輸出** | 根據客戶歷史需求自動調整 | 使用客戶偏好參數調整 Prompt |
| **多輪對話** | 支援問答式互動 | 實現對話狀態管理 |

### 5.2 互動流程範例

**範例 1：地區選擇**
```
用戶輸入：「2026年2月27日要在東京拍五大拉麵店 VS. 特輯」

AI 回應：「好的！為了提供最精準的推薦，請先告訴我：
1. 您想在哪個地區拍攝？六本木、澀谷、新宿、還是其他地區？
2. 您希望推薦的標準是什麼？人氣、口味、還是特色？」

用戶回答：「澀谷，要人氣高的」

AI 回應：「了解！以下是澀谷地區五個現時最熱門的拉麵店...」
```

**範例 2：輸出格式選擇**
```
用戶輸入：「幫我生成內容」

AI 回應：「您希望以什麼形式輸出？
1. 影片講稿（口語化，適合鏡頭前朗讀）
2. 文章或部落格稿件（文字化，適合發佈）
3. 社交媒體貼文（短句、吸睛標題）
4. 策劃大綱（結構化，方便團隊執行）」

用戶回答：「影片講稿」

AI 回應：「好的！以下是口語化的影片講稿...」
```

### 5.3 偏好記錄機制

- **輸出格式偏好**：用戶最常使用的格式
- **語氣風格偏好**：口語化、專業化、故事化
- **模組偏好**：用戶最常需要的模組（地址、歷史背景等）
- **地區偏好**：用戶常搜尋的地區

## 6. 最終目標

打造一個 AI 助手，能自動執行以下流程：

```
搜尋 → 驗證 → 整理 → 互動提問 → 生成 → 靈感拓展
```

並依照客戶的後續需求，輸出不同形式的內容，成為網紅或創作者的靈感來源工具。

**新增目標**：
- 實現智慧互動，主動幫助客戶縮小範圍
- 記錄客戶偏好，提供個性化服務
- 支援多輪對話，而非單次輸入輸出

## 7. 技術實現考量

### 6.1 必須遵守的規範
根據 README.md 的核心規則：

1. **禁止使用靜態模板**（規則 #7）
   - 所有內容必須通過 AI API 即時生成
   - 每次生成都是獨一無二的內容

2. **禁止硬編碼文字**（規則 #6）
   - 所有 UI 文字必須使用 `i18n` 系統
   - 支援 zh-TW/en/ja 三種語言

3. **禁止擅自生成程式代碼**（規則 #12）
   - 必須先檢查所有規範和架構要求
   - 必須檢查 i18n key、API 端點、資料模型

### 6.2 需要確認的事項
在制定實施計劃前，需要確認：

1. **實現方式**：
   - 完全替換現有功能？
   - 增強現有功能（保留簡單搜尋，新增進階模式）？
   - 並行實現（保留舊功能，新增「進階靈感助手」模式）？

2. **資料來源優先順序**：
   - 官方網站優先？
   - 媒體報導優先？
   - 平衡搜尋？
   - 用戶可選擇優先順序？

3. **驗證機制實現方式**：
   - 如何交叉比對？
   - 如何驗證真實性？
   - 如何引用來源？

4. **輸出格式選擇方式**：
   - UI 如何讓用戶選擇輸出格式？
   - 如何讓用戶選擇需要的模組？
   - 如何讓用戶選擇語氣風格？

## 8. 技術實現挑戰（新增）

### 8.1 智慧互動實現

**挑戰 1：多輪對話狀態管理**
- **問題**：如何管理對話狀態和上下文？
- **解決方案**：
  - 使用 Session 或資料庫儲存對話歷史
  - 實現對話狀態機（初始 → 提問 → 回答 → 生成）
  - 使用 AI 分析對話上下文，決定下一步動作

**挑戰 2：主動提問生成**
- **問題**：如何根據主題自動生成針對性問題？
- **解決方案**：
  - 使用 AI 分析主題，識別需要澄清的維度
  - 預設問題模板（地區、時間、風格、格式等）
  - 根據主題類型選擇相關問題

**挑戰 3：偏好記錄與應用**
- **問題**：如何記錄和應用客戶偏好？
- **解決方案**：
  - 在用戶資料庫中新增 `inspiration_preferences` 欄位
  - 記錄用戶的歷史選擇（格式、風格、模組等）
  - 在生成 Prompt 時自動加入偏好參數

### 8.2 UI/UX 設計挑戰

**挑戰 1：對話式介面**
- **問題**：現有 UI 是搜尋式，如何改為對話式？
- **解決方案**：
  - 保留搜尋功能，新增「智慧助手模式」
  - 實現聊天式介面（類似 ChatGPT）
  - 顯示 AI 提問和用戶回答的對話歷史

**挑戰 2：多輪互動流程**
- **問題**：如何引導用戶完成多輪互動？
- **解決方案**：
  - 顯示進度指示器（步驟 1/3：選擇地區）
  - 提供快速選擇按鈕（例如：六本木、澀谷、新宿）
  - 允許用戶跳過某些問題

### 8.3 後端架構調整

**需要新增的功能**：
1. **對話管理服務** (`conversation_service.py`)
   - 管理對話狀態
   - 儲存對話歷史
   - 生成下一步問題

2. **偏好管理服務** (`preference_service.py`)
   - 記錄用戶偏好
   - 應用偏好到 Prompt
   - 分析偏好趨勢

3. **互動式 Prompt 生成** (`interactive_prompt_builder.py`)
   - 根據主題生成問題
   - 根據回答調整 Prompt
   - 整合偏好參數

## 10. ⚠️ 必須注意 & 容易錯誤的五大重點（CRITICAL）

> **重要**：這五點是設計這個 AI 助手時的核心挑戰。最常見的錯誤就是「虛構資訊」和「互動不足」，這兩個問題會直接影響客戶的信任與使用體驗。

### 10.1 資料真實性與來源驗證

**必須注意**：
- 所有輸出內容要基於可靠來源（官方網站、媒體、維基百科、餐飲平台）
- 必須交叉比對多個來源，驗證資訊真實性
- 所有資訊必須附上來源連結

**容易錯誤**：
- ❌ AI 直接生成未經驗證的資訊，導致虛構或錯誤
- ❌ 沒有驗證機制，導致輸出錯誤資訊
- ❌ 沒有引用來源，無法追溯資訊來源
- ❌ 影響客戶信任

**解決方案**：
- 實現多來源搜尋機制
- 實現交叉比對驗證邏輯
- 在輸出中強制引用來源
- 如果無法驗證，明確標註「未驗證」或「AI 推測」

---

### 10.2 智慧記錄與個人化輸出

**必須注意**：
- 助手要能記錄客戶過往需求（例如：偏好地區、輸出形式）
- 在後續互動中自動調整輸出
- 避免重複問已回答過的問題

**容易錯誤**：
- ❌ 記錄不完整或錯誤，導致輸出與客戶需求不符
- ❌ 重複問已回答過的問題
- ❌ 忘記客戶的偏好設定
- ❌ 每次對話都從零開始，沒有記憶

**解決方案**：
- 實現用戶偏好資料庫
- 實現對話歷史記錄
- 在生成 Prompt 時自動加入偏好參數
- 實現偏好驗證機制（檢查是否已有記錄）

---

### 10.3 主動互動設計

**必須注意**：
- 助手不能只是被動回答，要主動提出問題
- 幫助客戶縮小範圍（例如：指定地區、輸出形式）
- 問題要精準、有針對性

**容易錯誤**：
- ❌ 提問過於模糊或冗長，讓客戶覺得繁瑣
- ❌ 失去「智慧互動」的體驗
- ❌ 問太多不必要的問題
- ❌ 問題沒有針對性，無法幫助客戶

**解決方案**：
- 實現智能問題生成（根據主題生成針對性問題）
- 限制問題數量（最多 3-5 個關鍵問題）
- 提供快速選擇按鈕（例如：六本木、澀谷、新宿）
- 允許用戶跳過某些問題

---

### 10.4 輸出形式的靈活性

**必須注意**：
- 輸出要根據客戶需求而定
- 可以是影片講稿、文章、社交貼文或策劃大綱
- 不能固定輸出一種格式

**容易錯誤**：
- ❌ 程式設計時固定輸出一種格式（如影片講稿）
- ❌ 忽略客戶的多樣化需求
- ❌ 沒有讓客戶選擇輸出格式
- ❌ 所有輸出都一樣，沒有個性化

**解決方案**：
- 實現輸出格式選擇器（UI）
- 實現多種 Prompt 模板（對應不同格式）
- 在生成前詢問客戶需要的格式
- 記錄客戶的格式偏好，後續自動應用

---

### 10.5 上下文管理與持續一致性

**必須注意**：
- 助手要能保持上下文一致
- 避免在不同回合中自相矛盾
- 記住之前的設定和對話內容

**容易錯誤**：
- ❌ 在多輪對話中遺失上下文
- ❌ 忘記之前的設定
- ❌ 導致輸出不連貫
- ❌ 自相矛盾的輸出

**解決方案**：
- 實現對話狀態管理（Session）
- 實現上下文儲存機制（資料庫）
- 在每次生成時包含完整的對話歷史
- 實現一致性檢查機制

### 10.6 檢查清單（開發時必須遵守）

在開發過程中，必須定期檢查以下項目：

#### 資料真實性檢查
- [ ] 所有輸出內容都有來源連結
- [ ] 實現了多來源交叉比對
- [ ] 無法驗證的資訊有明確標註
- [ ] 沒有虛構或錯誤資訊

#### 智慧記錄檢查
- [ ] 用戶偏好正確記錄在資料庫
- [ ] 對話歷史完整保存
- [ ] 不會重複問已回答過的問題
- [ ] 偏好參數正確應用到 Prompt

#### 主動互動檢查
- [ ] AI 會主動提出針對性問題
- [ ] 問題數量適中（不超過 5 個）
- [ ] 提供快速選擇按鈕
- [ ] 用戶可以跳過問題

#### 輸出靈活性檢查
- [ ] 支援多種輸出格式（影片講稿、文章、貼文、大綱）
- [ ] 用戶可以選擇輸出格式
- [ ] 不同格式使用不同的 Prompt 模板
- [ ] 記錄用戶的格式偏好

#### 上下文一致性檢查
- [ ] 對話狀態正確管理
- [ ] 對話歷史完整保存
- [ ] 每次生成包含完整上下文
- [ ] 輸出不會自相矛盾

## 11. 專家回覆與建議（技術決策）

### 11.1 來源驗證的嚴格程度

**專家建議**：
- **至少需要 2 個獨立來源確認**，尤其是涉及商業、品牌或地點資訊
- **未驗證資訊**：可以輸出，但必須明確標註「未驗證」，並提醒客戶需自行再確認
- **透明度原則**：既保持透明度，也避免誤導

**技術實現**：
- 實現多來源搜尋機制（至少 2 個來源）
- 實現交叉比對驗證邏輯
- 實現未驗證資訊標註機制
- 在輸出中明確標註驗證狀態

---

### 11.2 偏好記錄的範圍

**專家建議**：
需要記錄以下偏好：
- **主題類型**：餐飲、旅遊、品牌故事
- **輸出形式**：影片講稿、文章、社交貼文、大綱
- **語氣風格**：口語化、專業化、故事化
- **地區或語言偏好**：例如：東京六本木、香港、日文/英文

**設定方式**：採用「混合模式」
- **用戶可手動設定**：明確需求
- **AI 也能自動學習**：根據過往互動推斷

**技術實現**：
- 實現用戶偏好資料庫結構
- 實現手動設定 UI
- 實現自動學習機制（分析過往互動）

---

### 11.3 問題生成的策略

**專家建議**：
採用 **AI 動態生成 + 預設模板結合**
- **預設模板**：確保基本問題不會遺漏（如地區、輸出形式）
- **動態生成**：根據上下文提出更精準的問題
- **數量限制**：最多 3 個問題，避免過度打擾客戶

**技術實現**：
- 實現預設問題模板庫
- 實現 AI 動態問題生成
- 實現問題數量限制（最多 3 個）
- 實現問題優先級排序（重要問題優先）

---

### 11.4 輸出格式的選擇

**專家建議**：
- **在生成前，必須讓客戶選擇輸出格式**，確保符合需求
- **快速模式**：支援一鍵生成預設格式（例如：影片講稿），適合客戶趕時間時使用

**技術實現**：
- 實現輸出格式選擇器（UI）
- 實現快速模式（使用預設格式）
- 實現格式偏好記錄（後續自動應用）

---

### 11.5 上下文管理的範圍

**專家建議**：
- **對話歷史**：保留最近 10–20 回合，確保短期連貫性
- **跨 Session 記憶**：建議支援，因為客戶可能會在不同日期延續同一專案
- **記憶清理機制**：讓客戶能刪除或更新偏好，避免過時資訊干擾

**技術實現**：
- 實現對話歷史儲存（最近 10–20 回合）
- 實現跨 Session 記憶（資料庫持久化）
- 實現記憶清理機制（用戶可刪除或更新偏好）

---

### 11.6 ⚠️ 額外五個注意事項

#### 1. 避免過度依賴單一來源
- **注意**：即使是官方網站，也要交叉比對，因為有時候更新不及時
- **實現**：實現多來源搜尋，不依賴單一來源

#### 2. 互動節奏控制
- **注意**：提問要簡潔，不要一次丟太多問題，否則客戶會覺得繁瑣
- **實現**：限制問題數量（最多 3 個），提供快速選擇按鈕

#### 3. 多語支援
- **注意**：必須能同時處理中文、英文、日文，並根據客戶需求切換
- **實現**：實現多語言支援（zh-TW/en/ja），根據用戶語言偏好自動切換

#### 4. 透明度設計
- **注意**：在輸出時，明確標註哪些資訊已驗證、哪些未驗證，提升信任度
- **實現**：在輸出中標註驗證狀態，提供來源連結

#### 5. 錯誤回復機制
- **注意**：當無法找到資料時，要誠實告知「目前無法確認」，而不是硬生成
- **實現**：實現錯誤處理機制，誠實告知無法確認的資訊
